# Independent raid stall trace reading

Archived inputs and supporting outputs are in [raid-stall-traces-20261104](raid-stall-traces-20261104/): `trace.json.gz` and `dawn.json.gz` correspond to the two original `.cache` paths used below. The later request/inventory capture and consolidated diagnosis are documented in [raid-stall-diagnosis-20261104.md](raid-stall-diagnosis-20261104.md).

Input: `.cache/raid-stall-trace.json`, Chromium/Edge CDP trace and accompanying metadata. Window: `WG_RAID_TRACE_START` timestamp 171821267005 µs through +6,500 ms. No browser was launched for this analysis. The metadata lists an NVIDIA GeForce GTX 1660 and Microsoft Basic Render Driver; that inventory alone does not identify every traced context. Trace summary reports no recorded data loss.

V8 profile chunks were joined to their `Profile` by `(pid,id)`, not chunk `tid`, and sample time was reconstructed from the profile `startTime` and successive `timeDeltas`. Numbers below are sampled estimates and rounded to milliseconds. Inclusive stacks overlap; they must not be added together. Chunk ordering and sampling resolution limit precision.

- The graphics presentation Worker is profile `pid 11484, id 0x4`, profile thread 5340. In the 6.5-second window it sampled approximately 3,666 ms idle and 2,789 ms inclusive in `confirmed-presentation-stream.port.onmessage`; 2,580 ms inclusive was `webgpu-agriculture-vfx.sync` and 2,507 ms included `vfx-native.floorAt → localSurface → surface → Raycaster.intersectObject`. Triangle intersection and geometry access dominate those sampled stacks. Its longest traced `port.onmessage` task was 502 ms at +4,862 ms; another was 376 ms at +4,486 ms.
- The floor-query stack was not present in the first three seconds in these samples; approximate exclusive sample bins for +3–4, +4–5, +5–6 and +6–6.5 seconds were 145, 968, 965 and 429 ms. Thus this CPU work overlaps the later freeze but starts after the GPU process saturation. The trace does not establish that it caused the missing main-thread frames.
- The host Worker profile `id 0x1` sampled about 6,486 ms idle and the authority Worker `id 0x2` about 6,382 ms idle. The authority's sampled `execute` inclusive time was about 104 ms, including serialization and simulation. These are sampled proportions in the stated window, not a general performance assessment.
- The renderer main thread profile `id 0x3` sampled about 6,054 ms idle. A sampled `frame → renderFrameUpdates → sync → NativeWall.update → wallBridge` path exists, as does confirmed-state reconciliation, but neither measurement implies a several-second main-thread JavaScript task.
- `CrGpuMain` is pid 27500, tid 27360. Twenty-eight `WebGPU` duration events overlap the window, totaling approximately 6,429 ms wall time and 6,384 ms estimated thread CPU after proportional boundary clipping. Nested events include `CommandBufferService:PutChanged` with handler `WebGPUDecoderImpl`. Individual WebGPU events include about 1,171 ms at +599 ms and 1,148 ms at +3,159 ms. These are overlapping nested trace scopes, not additional durations to sum. `RasterDecoderImpl::DoWritePixelsINTERNAL` accounts for roughly 24 ms of wall time in this window.
- No event names in the window explicitly identify `createRenderPipeline`, `createShaderModule`, `createTexture`, `createBuffer`, `writeTexture`, `writeBuffer`, or queue submission. The graphics Worker V8 samples include about 2 ms inclusive under a function named `writeBuffer`, and no named samples for pipeline/shader/texture/buffer creation. Short native calls can be absent from V8 samples, and `WebGPUDecoderImpl` does not expose individual commands here. The trace therefore cannot determine which specific GPU operations consumed the decoder time.
- Renderer `Compositor` pid 11484 tid 23568 and GPU-process `VizCompositorThread` pid 27500 tid 11728 show no individual traced task above 1 ms in the window. The first recorded renderer `BeginFrame` is at about +4,913 ms; `DrawFrame` occurs around +4,937, +6,466 and +6,486 ms. Absence of long compositor CPU tasks is not proof of the precise reason frame delivery stopped.

This evidence identifies concurrent expensive GPU-process command decoding and a later Worker CPU episode in terrain queries for VFX. It does not distinguish shader compilation, pipeline creation, resource upload, GPU execution or driver behavior within the long WebGPU scopes, and does not independently establish causation for the frame gap. The local analysis script/output are `.cache/analyze-raid-profile.cjs` and `.cache/raid-independent-analysis.jsonl`.

## Independent second capture with Dawn categories

The second trace, `.cache/raid-stall-dawn.json`, includes `gpu.dawn` categories absent from the first capture. In the exact interval from `WG_RAID_TRACE_START` through +3,305 ms, 67 `DeviceBase::APICreateRenderPipeline` scopes on GPU-process `CrGpuMain` (pid 26076, tid 24980) overlap the window. Their clipped duration totals 3,163 ms wall and approximately 3,138 ms thread CPU. Sixty-five carry `renderPipeline_MeshStandardMaterial_*` labels (about 2,975 ms); one is `renderPipeline_atlas_1_1319` (143 ms) and one is `renderPipeline_MeshBasicMaterial_18` (45 ms). The 67 scopes contain 21 distinct label strings; several repeat three to five times. A repeated label does not establish identical WebGPU pipeline descriptors or explain its associated object.

All 69 `CompileShaderDXC` scopes in this interval are nested within those pipeline-creation scopes, totaling 2,916 ms wall and about 2,894 ms thread CPU. These are inclusive nested durations: do not add them to the pipeline total. Also nested are 69 Tint HLSL generation scopes (113 ms wall total) and 69 shader-module API scopes (69 ms wall total); category-specific instrumentation and scope boundaries matter when interpreting totals. This is direct evidence that DXC compilation occurred during pipeline creation in this second capture. It resolves the first capture's lack of attribution for this second run only; it does not retroactively identify the individual commands inside the first trace's opaque WebGPU scopes.

The GPU process shows WebGPU scopes covering approximately 3,289 ms of this window. Its longest `RunTask` spans are approximately 245, 551, 665 and 1,828 ms, with near-equal thread CPU time. On renderer main pid 14740 tid 24192, the longest `RunTask` overlapping the window is about 5.17 ms. The first main-thread `FireAnimationFrame` after the start appears at +3,306.7 ms. GPU-process `VizCompositorThread` has about 1.84 ms of traced RunTask wall time in the window (longest 0.088 ms); there are no renderer Compositor `RunTask` events in that interval. This establishes tight temporal overlap, not a complete compositor/driver causal proof.

There are 69 pipeline-creation scopes and 3,285.14 ms wall in the **whole post-start trace**, rather than 67: the final two `MeshBasicNodeMaterial_1443` scopes occur later at +4,715 and +4,801 ms. The distinction explains the different counts without contradicting the whole-trace summary. Current labels alone do not map Three.js material IDs to scene objects, geometry, shadow/depth state or exact pipeline keys. Local supplementary output: `.cache/raid-dawn-independent.txt`.
