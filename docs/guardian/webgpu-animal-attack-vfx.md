# Animal attack effects in the experimental WebGPU world

The development WebGPU scene enables the existing `attackVfxPlans` against the confirmed simulation state and retained `AnimalLogicalHit` facts. The Worker shares the existing native VFX atlas with agricultural spells, owns the resulting sprite effects and removes them when their confirmed plans expire. This layer does not cause hits or alter simulation. The status includes the actual prepared sprite count so a created but empty effect is not mistaken for rendered particles.

`tests/webgpu-agriculture-vfx.test.js` checks shared atlas use, attack-ID deduplication, confirmed hit continuity, prepared sprites and cleanup; `tests/attack-vfx.test.js` covers the native attack plans. `tools/experiments/audit_webgpu_combat_vfx.mjs` uses a strict WebGPU OffscreenCanvas Worker with a controlled warthog hit and observed 4,654 non-background pixels. `tools/experiments/audit_live_webgpu_combat_vfx.mjs` starts an actual development raid and waits for a naturally occurring combat effect with visible terrain and at least one prepared sprite. One run observed attack-382 with 16 sprites at confirmed sequence 587, with 13 animals ready and no reported simulation fault. These tests do not establish visual parity, time-to-first-use, frame-time or overall performance.

This is the animal-attack sprite layer only. Rigid debris, ribbons, local lights, soft-particle depth, guardian Attack projectiles and other combat/magic effects still require their own WebGPU integration and visual comparison. The actual game audit confirms populated sprite geometry rather than independently attributing screen pixels to a specific effect. The WebGPU scene remains under a development flag and the legacy scene continues to execute underneath.
