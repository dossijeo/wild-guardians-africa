# Sabana spatial-authority prototype — experimental

This prototype is isolated on `codex/hierarchical-navigation-openra`. It changes no production generator, navigation entry point, gameplay rule or save file. Build the binary with `tools/build-spatial-savanna-wasm.sh` under Emscripten, then run `node --test tests/spatial-savanna-prototype.test.js`, `node tools/experiments/benchmark-spatial-savanna.mjs`, `node tools/experiments/benchmark-spatial-savanna-two-chunks.mjs`, `node tools/experiments/benchmark-spatial-savanna-residency.mjs` and `node tools/experiments/benchmark-spatial-profile-switch.mjs docs/qa/hierarchical-navigation/spatial-profile-switch-dual-graph.json`.

## Existing responsibilities and proposed replacement

| Current code | Current responsibility | Spatial-core direction |
| --- | --- | --- |
| `src/world/terrain.js` `TerrainField` | Seeded relief, fluid, settlement terrain, surface and slope | C++ height/fluid source, exposed as visual buffers and direct logical queries |
| `src/world/terrain.js` `scatterWorld` | Seeded positions and asset slots for visual props; `Navigation.chunk` regenerates these to collide | C++ prop records used by both the render adapter and collision occupancy |
| `src/rendering/chunk-data.js` / `chunk-worker.js` | Rebuild terrain mesh, water, ground mask and props in a worker | Worker requests a WASM chunk and passes its render buffers to Three.js; ownership and transfer have a browser proof, but production integration remains open |
| `src/world/navigation.js` | Calls `TerrainField`, `propsAt`, structure collision, `walkable` and `segmentClear` | Authorized topology events update the C++ occupancy/sector graph; JS retains movement and gameplay decisions |
| `src/world/hierarchical-wasm/lazy-sectors-adapter.js` | Repeatedly calls JS geometry to rasterize each sector | The C++ generator fills the existing sparse-sector core directly |

Three.js meshes, textures, LOD, lighting, asset pack slots, animations, UI, audio and the game simulation remain JavaScript responsibilities. This experiment uses the existing C++ sparse-sector graph and route function in the **same WASM module** as a deterministic Sabana chunk generator. No JS geometry callback is made during generation, sector construction or route search. Render heights, vertex colors, river occupancy and 20 asset-slot prop positions are read from WASM buffers. The adapter constructs `THREE.BufferGeometry` for terrain and river, plus instance records for the game's Sabana models. Multiple requested chunks keep their logical rasters in resident graphs; loading a neighbor connects boundary sectors and permits routes across their seam. Evicting a chunk removes its sectors and regenerating it reuses the vacant sector slots. Wall edits refresh only intersected sectors. The worker and animal graphs have separate movement-radius rasters while sharing one procedural terrain, obstacle and wall authority.

## Reproducible measurements

The [ABBA report](spatial-savanna-prototype.json) uses Sabana seed 712 and one 48 × 48 m chunk on this host. It compiles each WASM module before timing, then measures visual preparation plus 16 sectors of animal-radius navigation. The baseline builds the current visual chunk and separately asks JS geometry to sample the existing sparse C++ graph. Both rows include preparing the visual data, not just A*.

| Pipeline | Initial visual + navigation | Navigation portion | JS geometry calls while loading sectors | Visible props |
| --- | ---: | ---: | ---: | ---: |
| Current JS world + sparse WASM | 332–429 ms | 279–346 ms | 2,789 `walkable`; 5,202 `segmentClear` | 202 |
| C++ shared spatial source + sparse graph | 17–36 ms | 14–20 ms | 0 | 236 |

The prototype binary is 58,940 bytes and each instance initially reserves 4 MiB of WASM linear memory. Its C++ wall add/remove operation took about 0.6–1.1 ms per edit and rebuilt only the intersected sectors. The current baseline's wall edit was **not** benchmarked in this report, so the edit times are not comparative. Route batches found 3 and 6 paths respectively because the worlds are intentionally different; route counts must not be compared as an algorithm-quality score. Tests confirm deterministic regeneration, matching adjacent terrain seams, a shared visible-prop collision point, neighbor-owned prop collision across a chunk seam, river occupancy exposed to the renderer, valid physical edges for returned worker and animal routes, and wall closure/breach recovery. The measured chunk has three collision-only props owned by neighbors; they are not duplicated visually.

The [two-chunk ABBA report](spatial-savanna-two-chunks.json) measures both 48 × 48 m visual chunks and 32 animal-radius sectors. The current JS generator plus JS physical sampling took 589–737 ms, including 5,671 `walkable` and 11,764 `segmentClear` calls. The C++ spatial source and resident graph took 40–54 ms with no JS geometry calls. Adding the second C++ chunk, including its generation, static raster and sector connections, took 18–20 ms. The two-chunk route test verifies that a cross-border route is valid, a wall across that border prevents a direct crossing, removing the wall reopens it, and rebuilding the worker profile preserves the crossing. Other tests cover negative chunk coordinates and requesting both chunks before the first graph build. These pipelines still generate different worlds and do unequal visual work, so the timing does not establish production readiness.

The [80-chunk residency traversal](spatial-savanna-residency.json) held exactly two chunks and 32 sector slots throughout, with 4 MiB of WASM linear memory before and after; adding the next chunk took 15.8 ms median and 18.7 ms at p95. This measures a straight-line QA traversal only, not a running game or Web Worker. A removed middle chunk is classified as **unknown**, rather than falsely blocked, when its absent connectivity might provide a route. The unbuilt border keeps the known physical outbound possibilities without generating the absent chunk. A wall across the currently resident area can likewise leave a longer route through unloaded terrain unknown; tests check that the local crossing is blocked and that the route is restored after wall removal.

The [zigzag residency traversal](spatial-savanna-zigzag.json) adds a non-linear 8×8 serpentine path and reverses it, with a four-chunk viewport. Across 127 positions it visited 81 unique chunks, regenerated 175 previously seen chunks, validated a physically traversable route at every position, and performed 16 local wall add/remove cycles. A second deterministic run matched all non-timing counts. Both runs stayed at 64 sector slots and 4 MiB of WASM linear memory. Streaming a viewport step, including visual-buffer hashing for QA, took 43–44 ms median and 50–53 ms at p95 on this host. This is a bounded QA traversal, not sustained game streaming; it establishes that turning and revisiting do not grow the graph or change generated chunks. A shorter turning-viewport case is now part of the automated regression suite.

The [single-graph profile baseline](spatial-profile-switch-baseline.json) and [dual-graph follow-up](spatial-profile-switch-dual-graph.json) use the same four-chunk Sabana seed and alternate the worker (0.28 m) and animal (1.1 m) profiles 20 times each. They each include one cold graph build per profile. With the original single graph, the 19 warm worker switches took 1,481.8 ms in total (76.6 ms median), and the animal switches took 1,294.7 ms (67.0 ms median). Keeping both graphs resident reduced these 19-switch totals to 0.013 and 0.015 ms respectively in one local run. The cold builds took 109.1 and 86.2 ms after the change, versus 91.2 and 70.8 ms in the baseline; building two graphs is still real work. Both runs reported a 4 MiB WASM linear-memory allocation, which does not measure live allocation inside that reservation. An automated regression now checks both profiles after repeated switches, wall closure/reopening and chunk eviction/reload; switching alone must not increment either graph's sector-update counter. These timings measure the isolated WASM module, not the game's full frame or campaign cost.

Keeping both profiles resident initially doubled streaming work. In a four-pair ABBA [baseline traversal](spatial-dual-profile-streaming.json) of 80 steps and two resident chunks, one animal graph took 19.9–20.7 ms median per step; worker plus animal graphs took 40.7–42.5 ms. Each chunk was generated once, but the rasterizer redundantly tested both endpoints and both directions of every interior connection. The [updated traversal](spatial-dual-profile-streaming-optimized.json) uses already sampled endpoint passability and evaluates each symmetric interior connection once; one graph takes 8.0–9.6 ms median and two take 16.5–17.3 ms. The one-graph result also improved, so this is a reduction in work rather than a profile-specific shortcut. Initial graph construction and updates for both radii still cost more than one graph. These samples ran in the isolated WASM adapter on this host, without Three.js upload or gameplay.

The raster optimization was checked against the previous committed WASM binary, not merely against route examples. The [equivalence report](spatial-raster-equivalence.json) compares 165,888 cell-passability results and 331,776 directed edge queries across four resident chunks, seeds 28 and 712, worker, ordinary-animal and large-animal radii, and open, walled and reopened states. All results matched. The regression suite also checks routes, streaming and wall edits. Future directional movement rules would require separate outbound and inbound edge sampling rather than the present symmetric shortcut.

The solid-prop raster now uses local 8 m buckets instead of scanning every rock and large tree for every cell and edge sample. A full 48 × 48-cell comparison against all visible solid props in the surrounding nine chunks agrees for worker, ordinary-animal and rhinoceros radii (0.28, 1.1 and 1.55 m). The preceding single-run benchmark measured 20–23 ms of C++ navigation preparation; the updated single-run range is 12–17 ms. This is a diagnostic comparison across runs, not a controlled claim about a precise speedup. Profiles above 2 m are explicitly rejected until the bucket envelope is extended.

The browser QA page at `tests/browser/spatial-savanna-prototype.html` loaded the actual Sabana biome asset pack into the 20 instance slots and rendered 236 props, the terrain and a river from the prototype's WASM data. Manual inspection in the in-app browser showed the river and props in the expected positions without JavaScript errors. That initial session saved no screenshot. The later [seed 712 side-by-side capture](screenshots/sabana-seed-712-js-vs-wasm-1600x900.png) and [seed 28 capture](screenshots/sabana-seed-28-js-vs-wasm-1600x900.png) provide reproducible browser evidence, with [capture metadata](screenshots/capture-report.json). The C++ scene uses the game's actual Sabana models and has coherent visible water and obstacles, but its ground is flatter and more uniformly tinted, the vegetation distribution is denser, and its pond and river placement differ. The differing positions are permitted by the experimental brief, but the material treatment and relief are not yet representative enough for visual acceptance. Both sides of this QA page use a simplified shared sky, lighting and water material rather than the full in-game scene; these captures cannot establish final in-game fidelity. `tools/experiments/capture-spatial-savanna-visual.mjs` reproduces the captures with a local Vite server and Playwright.

A [ground-sample measurement before the color adjustment](spatial-savanna-ground-measurements.json) showed that height variance is seed-dependent: the C++ height standard deviation was 0.60 m versus 1.25 m in JS for seed 712, but 1.27 m versus 0.80 m for seed 28. Therefore simply increasing relief everywhere would be unjustified. The consistent gap was vertex-color variation: C++ luminance standard deviation was 0.030–0.035 versus 0.064–0.068 in JS. The C++ renderer now mixes the Sabana pack's soil, grass and rock colors with slope, dry patches and river-bank sand. The [follow-up samples](spatial-savanna-ground-palette.json) measured C++ luminance variation of 0.057–0.059. [Updated seed 712](screenshots/sabana-seed-712-js-vs-wasm-palette-1600x900.png) and [seed 28](screenshots/sabana-seed-28-js-vs-wasm-palette-1600x900.png) browser captures show warmer, more varied ground, without claiming parity with the production material. The [ABBA timing report](spatial-savanna-palette-benchmark.json) measured a 7.65 ms median for the previous generation-plus-animal-graph path and 8.14 ms for the palette version on this host; the difference is small but measurable. [Raster equivalence](spatial-raster-equivalence-palette.json) confirms 165,888 cell and 331,776 edge decisions still match the prior navigation binary after this purely visual change.

The spatial core now also emits the game's 35×35 RGBA8 ground-mask buffer in the same `populateChunk` call as heights, water and obstacles: vegetation cover, broad variation, moisture and settlement wear. Before a settlement is requested its wear channel is zero. It reuses the C++ seed, river and noise source and does not ask JavaScript to regenerate the mask. Tests check its length, deterministic regeneration and byte-identical three-column overlap between adjacent chunks. A [real browser worker transfer](spatial-ground-mask-transfer.json) returned the buffer with the other visual payloads, confirmed their lengths and the terrain seam, and reported 64,684 transferred bytes for the first prototype chunk versus 503,644 bytes for the current worker. These payloads do different visual work, so the byte difference is diagnostic only. A [12-pair ABBA run](spatial-ground-mask-benchmark.json) measured 8.51 ms median for the prior generation-plus-animal-graph binary and 8.72 ms with the new mask. The optional browser comparison now applies the **same production `BiomeGround` textures and `AfricanToon` shader** to both scenes, supplying each side's respective mask. The [seed 28 capture](screenshots/sabana-seed-28-js-vs-wasm-game-ground-1600x900.png) and [seed 712 capture](screenshots/sabana-seed-712-js-vs-wasm-game-ground-1600x900.png) show substantially closer ground treatment than the basic-material preview, with no browser shader or JavaScript errors in the [capture report](screenshots/capture-report-game-ground.json). The visual recipes still differ and this comparison omits the game's sky, contact shadows and surrounding chunks; shore behavior requires in-game validation.

An optional settlement command now calculates a site level from the **C++ relief**, flattens its rectangular footprint with a smooth margin, clears nearby procedural props and ponds, and writes the ground material's wear channel. Both resident worker and animal graphs are refreshed for the affected loaded chunks. The river mesh uses the same fluid predicate as navigation when flattening dries part of a river strip; an automated case covers that overlap. This remains a QA prototype: the game has not started sourcing settlement placement or construction from WASM, and no building is instantiated by this command. [Seed 28](screenshots/sabana-seed-28-js-vs-wasm-settlement-game-ground-1600x900.png) and [seed 712](screenshots/sabana-seed-712-js-vs-wasm-settlement-game-ground-1600x900.png) show the cleared site with the game's ground material; the [browser capture report](screenshots/capture-report-settlement-game-ground.json) contains no page or console errors. The two procedural worlds differ visibly in river position and object distribution. These isolated images verify the rendering path, not production visual acceptance.

The prototype can now package its generated chunk for the **existing scene renderer**: indexed local terrain positions and C++ colors, local water triangles, the shared ground mask and the game's prop instance slots. `nativeTerrainBuffer` accepts this compact indexed shape while preserving its original interleaved JS input. The chunk transfer helper includes all five typed-array buffers. A regression performs a real structured-clone transfer, constructs both production geometry types and checks terrain coordinates, normals, colors and instances. The [seed 712 browser capture using this payload](screenshots/sabana-seed-712-js-vs-wasm-payload-settlement-1600x900.png), [seed 28 capture](screenshots/sabana-seed-28-js-vs-wasm-payload-settlement-1600x900.png) and [capture report](screenshots/capture-report-payload-settlement.json) confirm that this bridge renders with the game's ground material without browser errors. It is not yet selected by `NativeChunkStream` in gameplay, because navigation, collision and procedural visuals must change authority together.

The [render-payload measurement](spatial-chunk-payload.json) uses eight isolated desktop samples with a settlement and both navigation profiles. After the first warm-up, the compact payload was 92,188–93,412 bytes, its creation took 0.42–0.51 ms, structured-clone transfer took 0.23–0.31 ms, and the existing renderer's geometry constructors took 0.57–0.83 ms. The spatial generation plus both graph builds took 18.0–20.6 ms in those warm samples. These are Node timings without a real worker message, GPU upload, model instantiation or gameplay. The previous browser transfer report covers real worker messaging for an older payload, so these numbers must not be presented as a full game speedup.

The payload packer now has no Three.js dependency and runs inside a **real browser Web Worker**. The [worker transfer report](spatial-scene-payload-worker-transfer.json) exercises two adjacent settlement chunks. In this single desktop run, the first C++ worker response took 39.8 ms including 7.6 ms of module fetch/compile in that worker, and the second took 10.6 ms; the transferred visual buffers were 93,412 and 90,172 bytes. The current JS worker responses took 75.1 and 38.7 ms with 503,644 and 502,564 bytes, respectively. Different procedural worlds and visual detail still make these timing and size comparisons diagnostic rather than equivalent-work speedups. The receiving thread constructed the production terrain/water geometry, the two height seams matched, and no browser errors occurred. The same worker accepted a JS wall-construction command, changed a known cross-chunk route from `found` to `blocked`, then restored `found` after removal. Its measured wall add/remove operations took 1.3/0.5 ms and updated local sectors. The [raw-format regression](spatial-raw-worker-regression.json) separately confirms the previous QA worker response still transfers and retains its terrain seam. No worker-to-game mutation channel or save integration exists yet.

The worker implementation now lives with the experimental spatial core rather than inside the browser test. A [follow-up browser run](spatial-scene-payload-module-worker.json) built **both worker and animal navigation profiles** in that one WASM instance. A wall closed a cross-chunk route for both profiles and removing it reopened both. Evicting and re-requesting the neighboring chunk reproduced its positions, colors, water, ground mask and prop instances byte-for-byte, restored the route, and left the WASM linear-memory reservation at 4 MiB. This one run measured 1.5 ms for eviction and 19.2 ms for the reload roundtrip; the two-profile cold chunk responses were 48.6 and 18.5 ms. The [raw-response check after relocating the worker](spatial-raw-worker-module.json) also passed. This is still a QA client of the worker: gameplay has not switched its terrain, collision, placement, streaming or save ownership to the new core.

The core now retains **multiple settlement sites** rather than replacing the first when another village is founded. Its chunk-local index selects only sites whose terrain, cleared props or pond removal might affect the requested chunk; adding a distant site refreshes only nearby resident sectors. A resident chunk can be read again after a topology event without rebuilding its navigation. The focused regression adds a second site, verifies its flattened terrain and cleared props, reselects the first chunk without a graph update, and confirms replacing the site list removes the second site. In a [real worker run](spatial-multiple-settlements-worker.json), adding a second village updated 16 sectors of the active profile, changed the new village's visual chunk, left the first village's positions, wear mask and props byte-identical, and kept 4 MiB of WASM linear memory. The same run also rechecked wall closure, dual profiles, eviction and deterministic regeneration. A [scaling diagnostic](spatial-settlement-scale.json) added 50 and 250 distant sites with one local chunk resident; all six runs had the same terrain digest, and the median time to reselect the local chunk remained 0.78–0.93 ms, versus 0.81–0.83 ms with no distant sites. Registering 250 sites itself took 232–246 ms in this isolated batch, roughly 1 ms per rare village event. These measurements do not prove unbounded memory behavior or game integration.

The [settlement timing report](spatial-savanna-settlement.json) runs eight local isolated samples across seeds 712 and 28. Cold chunk generation took 0.81–3.64 ms, building the worker and animal graphs together took 12.2–31.4 ms, and applying the one-time site update took 13.8–20.7 ms. The site affected all 16 sectors of this small chunk in each graph; the counter rose by 16 because it reports the active graph's updates, not the sum across profiles. WASM linear memory stayed at 4 MiB in these samples. The first sample includes startup and JavaScript JIT effects, and visual-buffer readback excludes GPU upload. This benchmark does not yet include production village placement, workers, structures or an actual game session.

The [non-linear streaming rerun](spatial-savanna-zigzag-ground-mask.json) now includes the ground mask in each regenerated chunk's digest. Across two 127-step traversals, all 175 revisited chunks matched their first visual payload, routes were validated at every viewport position, and 16 wall edits completed. Sector slots stayed at 64 and WASM linear memory at 4 MiB. The measured median was 20.17 ms per viewport step including visual hashing, on this host. This is still isolated QA rather than game streaming.

The transferred terrain positions can now serve as a read-only JavaScript surface view without running a second procedural terrain recipe. `SpatialSurfaceView` retains the chunk's transferred `Float32Array`, samples its rendered triangles, and drops the view when the chunk is evicted. A focused test compared 500 interior samples across two chunks with the C++ source (absolute error below 0.00002 m), plus a shared edge, a settlement terrain update and eviction. The [real browser worker check](spatial-surface-view-worker.json) independently queried a point from C++ after transfer and found a 0.00000024 m difference; transfer, wall editing, regeneration and multi-settlement checks also passed. This is a consistency proof for render-height consumers. It does not yet replace gameplay's terrain queries, water and slope rules, placement checks or collision ownership, and the worker roundtrip is a QA comparison rather than a proposed per-frame query.

Dynamic rectangular barriers now share one C++ occupancy representation. The existing wall command creates a barrier closed to both profiles; a generic barrier can permit workers, animals, both or neither through a two-bit mask. Changing that mask or removing the barrier refreshes only intersected sectors in both resident graphs. The [Web Worker passage check](spatial-dynamic-passage-worker.json) used the same cross-chunk edge for each profile: workers passed the initially worker-only gate while animals could not; closing it blocked workers too; reopening it restored both. The addition refreshed two sectors of the active graph in that run, and add/close/reopen each measured approximately 0.2 ms with browser timer precision. The focused suite includes a no-op change (zero sector rebuilds), invalid mask, removal and both profiles. This is an isolated topology command, not yet wired to gameplay gate, building or save events.

That scaling benchmark exposed the linear barrier scan as a real issue. With 256 tiny barriers deliberately packed into one resident chunk, [before indexing](spatial-barrier-scaling-baseline.json), the cumulative add-and-local-update cost was 961–1,376 ms across three seeds. A chunk-local 8 m bucket index, used directly by the C++ collision raster and cleared on removal, brought the same [indexed run](spatial-barrier-scaling-indexed.json) to 209–312 ms. Sector-update counts and the benchmark's route outcomes matched exactly. The new regression checks 2,116 grid points and 4,232 directed local edges per profile against the baseline terrain plus explicit barrier geometry, then removes every barrier and checks restoration; all 24 focused tests pass. A [browser worker rerun](spatial-barrier-index-worker.json) also passed transfer, dynamic passage, wall edit, eviction/regeneration, settlements and surface-height checks with the indexed binary. Individual edits still rebuild their local sectors; batching a wall chain remains a potential improvement if measured construction patterns warrant it. The WASM module reserved 4 MiB in these samples, but this reservation does not measure heap allocations inside it.

## Limits before any game integration

This is evidence that eliminating repeated JS geometry queries can be valuable, **not** evidence of a complete or visually equivalent Sabana replacement. The C++ recipe uses simplified relief, river and prop placement. Its water is now clipped to its own wet terrain and can use the production water shader in isolated QA, but still lacks the production river-bank materials, detailed geometry and complete scene lighting. Settlement flattening, clearing and wear exist only as an isolated command; village placement, monument layout and full asset transform/variant rules remain absent. The ground-mask buffer now renders with the production ground shader in isolated browser QA, but not yet in the game. Its indexed Three.js ground geometry performs less visual work than the current production chunk builder. Side-by-side browser screenshots have now been saved and inspected, but full in-game and device QA remain open. The straight-line and zigzag traversals cover bounded eviction and regeneration, but actual game streaming and longer campaigns remain untested. The worker/animal graphs now persist concurrently, but additional animal radius classes and sustained memory behavior require measurement. The browser transfer proof does not cover sustained game streaming, Web Worker ownership during world mutation, mobile memory or save-version migration.
