# Sabana spatial-authority prototype — experimental

This prototype is isolated on `codex/hierarchical-navigation-openra`. It changes no production generator, navigation entry point, gameplay rule or save file. Build the binary with `tools/build-spatial-savanna-wasm.sh` under Emscripten, then run `node --test tests/spatial-savanna-prototype.test.js`, `node tools/experiments/benchmark-spatial-savanna.mjs`, `node tools/experiments/benchmark-spatial-savanna-two-chunks.mjs` and `node tools/experiments/benchmark-spatial-savanna-residency.mjs`.

## Existing responsibilities and proposed replacement

| Current code | Current responsibility | Spatial-core direction |
| --- | --- | --- |
| `src/world/terrain.js` `TerrainField` | Seeded relief, fluid, settlement terrain, surface and slope | C++ height/fluid source, exposed as visual buffers and direct logical queries |
| `src/world/terrain.js` `scatterWorld` | Seeded positions and asset slots for visual props; `Navigation.chunk` regenerates these to collide | C++ prop records used by both the render adapter and collision occupancy |
| `src/rendering/chunk-data.js` / `chunk-worker.js` | Rebuild terrain mesh, water, ground mask and props in a worker | Worker requests a WASM chunk and passes its render buffers to Three.js; ownership and transfer have a browser proof, but production integration remains open |
| `src/world/navigation.js` | Calls `TerrainField`, `propsAt`, structure collision, `walkable` and `segmentClear` | Authorized topology events update the C++ occupancy/sector graph; JS retains movement and gameplay decisions |
| `src/world/hierarchical-wasm/lazy-sectors-adapter.js` | Repeatedly calls JS geometry to rasterize each sector | The C++ generator fills the existing sparse-sector core directly |

Three.js meshes, textures, LOD, lighting, asset pack slots, animations, UI, audio and the game simulation remain JavaScript responsibilities. This experiment uses the existing C++ sparse-sector graph and route function in the **same WASM module** as a deterministic Sabana chunk generator. No JS geometry callback is made during generation, sector construction or route search. Render heights, vertex colors, river occupancy and 20 asset-slot prop positions are read from WASM buffers. The adapter constructs `THREE.BufferGeometry` for terrain and river, plus instance records for the game's Sabana models. Multiple requested chunks keep their logical rasters in one resident graph; loading a neighbor connects boundary sectors and permits routes across their seam. Evicting a chunk removes its sectors and regenerating it reuses the vacant sector slots. Wall edits refresh only intersected sectors. Worker and animal profiles can each be queried, currently by rebuilding this module's navigation profile.

## Reproducible measurements

The [ABBA report](spatial-savanna-prototype.json) uses Sabana seed 712 and one 48 × 48 m chunk on this host. It compiles each WASM module before timing, then measures visual preparation plus 16 sectors of animal-radius navigation. The baseline builds the current visual chunk and separately asks JS geometry to sample the existing sparse C++ graph. Both rows include preparing the visual data, not just A*.

| Pipeline | Initial visual + navigation | Navigation portion | JS geometry calls while loading sectors | Visible props |
| --- | ---: | ---: | ---: | ---: |
| Current JS world + sparse WASM | 332–429 ms | 279–346 ms | 2,789 `walkable`; 5,202 `segmentClear` | 202 |
| C++ shared spatial source + sparse graph | 17–36 ms | 14–20 ms | 0 | 236 |

The prototype binary is 58,940 bytes and each instance initially reserves 4 MiB of WASM linear memory. Its C++ wall add/remove operation took about 0.6–1.1 ms per edit and rebuilt only the intersected sectors. The current baseline's wall edit was **not** benchmarked in this report, so the edit times are not comparative. Route batches found 3 and 6 paths respectively because the worlds are intentionally different; route counts must not be compared as an algorithm-quality score. Tests confirm deterministic regeneration, matching adjacent terrain seams, a shared visible-prop collision point, neighbor-owned prop collision across a chunk seam, river occupancy exposed to the renderer, valid physical edges for returned worker and animal routes, and wall closure/breach recovery. The measured chunk has three collision-only props owned by neighbors; they are not duplicated visually.

The [two-chunk ABBA report](spatial-savanna-two-chunks.json) measures both 48 × 48 m visual chunks and 32 animal-radius sectors. The current JS generator plus JS physical sampling took 589–737 ms, including 5,671 `walkable` and 11,764 `segmentClear` calls. The C++ spatial source and resident graph took 40–54 ms with no JS geometry calls. Adding the second C++ chunk, including its generation, static raster and sector connections, took 18–20 ms. The two-chunk route test verifies that a cross-border route is valid, a wall across that border prevents a direct crossing, removing the wall reopens it, and rebuilding the worker profile preserves the crossing. Other tests cover negative chunk coordinates and requesting both chunks before the first graph build. These pipelines still generate different worlds and do unequal visual work, so the timing does not establish production readiness.

The [80-chunk residency traversal](spatial-savanna-residency.json) held exactly two chunks and 32 sector slots throughout, with 4 MiB of WASM linear memory before and after; adding the next chunk took 15.8 ms median and 18.7 ms at p95. This measures a straight-line QA traversal only, not a running game or Web Worker. A removed middle chunk is classified as **unknown**, rather than falsely blocked, when its absent connectivity might provide a route. The unbuilt border keeps the known physical outbound possibilities without generating the absent chunk. A wall across the currently resident area can likewise leave a longer route through unloaded terrain unknown; tests check that the local crossing is blocked and that the route is restored after wall removal.

The solid-prop raster now uses local 8 m buckets instead of scanning every rock and large tree for every cell and edge sample. A full 48 × 48-cell comparison against all visible solid props in the surrounding nine chunks agrees for worker, ordinary-animal and rhinoceros radii (0.28, 1.1 and 1.55 m). The preceding single-run benchmark measured 20–23 ms of C++ navigation preparation; the updated single-run range is 12–17 ms. This is a diagnostic comparison across runs, not a controlled claim about a precise speedup. Profiles above 2 m are explicitly rejected until the bucket envelope is extended.

The browser QA page at `tests/browser/spatial-savanna-prototype.html` loaded the actual Sabana biome asset pack into the 20 instance slots and rendered 236 props, the terrain and a river from the prototype's WASM data. Manual inspection in the in-app browser showed the river and props in the expected positions without JavaScript errors. No screenshot was saved from this browser session, so visual acceptance remains open. The river edge is visibly stepped and the terrain is less detailed than production.

The [Web Worker transfer report](spatial-savanna-worker-transfer.json) exercises the actual production `chunk-worker.js` and a QA-only WASM worker in the same local in-app browser, with seed 712 and sequential chunks `(0,0)` and `(1,0)`. Four page loads produced a first-request roundtrip of 87.7–167.5 ms for the current worker versus 43.5–59.8 ms for the WASM prototype; the second request took 45.1–48.3 ms versus 20.9–24.7 ms. The prototype's measured C++ generation plus navigation took 20.1–24.4 ms per chunk and copying its visual buffers out of WASM memory took 0–0.3 ms. Transferred prototype buffers totaled 47,328–47,888 bytes per chunk versus 502,564–503,644 bytes for the current worker's terrain, water and ground mask buffers. The first prototype request includes 4.2–13.9 ms to fetch and compile its module. The browser checks confirmed transferred buffer lengths, 2,401 terrain vertices and bit-identical heights along the adjacent chunk seam. A Three.js terrain geometry preparation on the receiving thread took 0.9–4.1 ms. These timings include worker messaging but not GPU upload, full prop instantiation or gameplay.

A [follow-up visual and timing check](spatial-savanna-ponds.json) adds deterministic Sabana ponds to the **same C++ source** that carves their terrain, places their existing model, supplies the water surface and marks the area impassable for animals. The side-by-side browser page `tests/browser/spatial-savanna-visual-compare.html?seed=28` shows the current JS chunk and the C++ chunk with identical biome assets, camera and lighting. Manual inspection confirmed the pond asset and water appear on carved terrain; a focused test verifies its visible water level and animal occupancy derive from the same generated pond. The browser worker transferred 56,180 bytes for the first pond-bearing chunk; its roundtrip took 48.4 ms, including 4.7 ms of WASM startup, and a second chunk took 20.3 ms. One local [ABBA run](spatial-savanna-ponds-abba.json) measured 24–43 ms for C++ visual preparation plus navigation versus 430–611 ms for JS generation plus JS physical sampling; the visual recipes and work performed still differ, so these are diagnostic timings only. The previous ABBA report remains unchanged.

This is a transfer-cost measurement, **not** an apples-to-apples production speedup. The two generators produce different terrain and props. The prototype omits much of the production water, ground-mask and prop payload, and its receiver performs less work. The sample consists of four local desktop page loads in the Vite development server; no mobile, packaged build or sustained streaming result is implied.

## Limits before any game integration

This is evidence that eliminating repeated JS geometry queries can be valuable, **not** evidence of a complete or visually equivalent Sabana replacement. The C++ recipe uses simplified relief, river and prop placement. It now has ponds but their and the river's water surfaces still use a coarse cell preview rather than the production treatment. It lacks settlement flattening, ground mask, monument layout and full asset transform/variant rules. Its indexed Three.js ground geometry also performs less visual work than the current production chunk builder. The comparison page was inspected, but no screenshot was saved or device QA accepted. Two adjacent chunks share routes, and the 80-chunk traversal covers local eviction, but non-linear streaming and longer campaigns remain untested. The single sparse graph is rebuilt when switching worker/animal radius; a game implementation needs persistent per-profile graphs without duplicating the procedural authority. The browser transfer proof does not cover sustained game streaming, Web Worker ownership during world mutation, mobile memory or save-version migration.

The next gate is a visually representative Sabana chunk with production-level river/ground treatment, captured rendering QA, and matched worker/animal route cases. Only then can a full chunk-to-first-route comparison justify extending the generator to the other five biomes and running sustained 14-night campaigns. The existing JS generator and navigator remain untouched until those gates pass.
