## What precedes app-world-load

The original smoke synchronously dispatches Start/Load-slot and sets worldStartedAt **after send returns**. startGame executes its synchronous prefix through its first await during that dispatch. Therefore the smoke interval is not click-to-controls and may exclude World constructor/preparation synchronous-prefix cost. The roughly29.9765s difference between worldWaitMs and active app-world-load elapsed is an approximate, separately sampled wall-clock gap, not an exclusive CPU span.

The remaining ordered work is:

1. await prepared.pending: diorama.prepare plus loading-frame images, concurrently. The preloading hook can start earlier in actual native menu interaction; original primary smoke sends Start directly. It does not use the prepare-loading action.
2. diorama preparation awaits sky **before** the catalogue requests and maize/bridge model requests. Sky.loadResources reads skies.json, fetches both panorama bodies concurrently, awaits each existing sky worker, then synchronously constructs textures/materials. It memoizes ready, so later World sky.load reuses this promise/resources. Assets.model similarly memoizes exact logical URLs, so diorama models are reused by World; this is not a repeated decode for the same URL.
3. Catalogues are concurrent, then maize and bridge GLBs are concurrent. Soil texture, mountain atlas, cooperative crop-batch construction and private material hooks follow in order. GPU preparation warms every maize stage/bridge: compile maize, screen upload, compile sky, compile mist, mist upload, day/night sky render, final fence. Those waits and synchronous submits are required for the prepared first diorama frame; not all await time is CPU/compile time.
4. After prepared.pending: ownership handoff, UI and first render. Continue additionally awaits loadPrepared/worker snapshot; New instead creates state and later awaits prepareInitialLocation. Both await biome/village metadata, build navigation/footprints/entries, resume state, construct HUD and attach handlers, before app-world-load begins. This particular run is primary randomized New, so its pre-world gap cannot be assigned to snapshot decode.

The observer is installed at the end of successful World construction, connected before diorama.prepare. Thus existing diorama awaited spans and synchronous submits are observed in original smoke. However the tracker deletes completed active rows and retains only **one lastCompleted** row. Later World submissions replace that row: the final snapshot does not retain completed pre-world durations. There is no evidence here measuring which early phase owns the30s gap. Constructor work precedes the hook. In DEV qa-loading main can replace onLoadingSpan and reconnect a new tracker; the original packaged smoke has no progressQa, so that replacement is not this run's cause. Weak ownership, terminal release and prior-hook restoration prevent retention of detached World/resources; only bounded scalar compile rows remain while active.

## Why 617 objects do not mean617 shader compilations

Three r180 compile traverses all submitted objects/materials, sets up the complete target scene lights, and calls getProgram. getProgram computes the actual parameter/cache key and reuses materialProperties.programs when the key exists; WebGLPrograms.acquireProgram also reuses an identical renderer-wide key across distinct materials. New cloned materials still need their own onBeforeCompile/uniform installation and common/environment/light properties. Submission of the same recipe is not necessarily creation of another native program. WebGLProgram.isReady latches true, so later reads of a ready program do not issue another COMPLETION_STATUS_KHR query.

The current raw directly illustrates reuse: eight distinct materials in batch5 selected only ready program18 and completed after one poll. Batch6 selected two native programs for eight objects. Its actual incomplete variant is resident Standard crop-bridge19; six associations do not prove six native compiles. The synchronous last submit took2.6ms. We have no cumulative CPU proof that repeated traversal/submission dominates.

A customProgramCacheKey, material UUID, or material identity alone is an unsafe dedup key. Three includes geometry tangents/colors/UVs/morph attributes and counts, skinning, instancing/morph/color, batching/color, scene lighting/shadows/fog/clipping, maps/material defines and screen target/output properties. Standard materials sharing a native program still require independent uniforms. Skipping an object's getProgram can skip a variant or initialization. Invisible crop stages/bridges are intentionally warmed for first appearance; filtering visible/count0 objects would weaken coverage.

Previously attempted parallel-per-group and single union readiness candidates already kept all submissions while moving waits to a collective barrier; both failed original native gates. The later shared diorama candidate combined sky/model overlap with that union and also failed. It did not isolate sky-first serialization. No-compression, animal-prefetch, pause-menu and shared-ground failed or lacked an isolated whole-gate acceptance. Do not relabel the union as a new dedup fix. Sources/protocols remain on codex/windows-loading-smoke; no old flags are imported here.
