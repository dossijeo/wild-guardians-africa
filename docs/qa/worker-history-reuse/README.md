# Reutilización de índices de historial de trabajadores

Se habilita explícitamente reutilización para plantas y cajas. Sus IDs son inmutables y el gameplay añade elementos o reemplaza arrays: la clave WeakMap es el array y el índice se invalida si cambia su longitud. Los campos vivos, entregados y otros estados se consultan sobre el mismo objeto actual. Las tareas conservan el índice local por paso; las colecciones pequeñas siguen usando búsqueda lineal y no crean el índice. Restaurar una partida produce arrays nuevos y no recupera objetos del estado anterior.

El índice se crea de forma diferida tras una segunda consulta; se evita reconstruir y recorrer todo el historial en cada updateWorkers. La prueba de100 nuevas funciones de consulta no lee de nuevo los IDs de la colección ya indexada; se verifican appends, retiradas por longitud, reemplazos y objetos restaurados. No se autoriza sustituir miembros in situ conservando longitud para estas colecciones con reuse; si se cambia esa regla habrá que invalidar explícitamente.

Hay campañas/suite en segundo plano; alternan referencia y candidata. No es una medición de FPS, GPU, RAM física ni balance vigente100 noches. Se conserva el baseline de Game y el helper anterior; la candidata de Game contiene el helper precapturado como dataURL. Las diferencias de comentario en el helper final no cambian su lógica.
