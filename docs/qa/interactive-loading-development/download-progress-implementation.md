# Download contribution: implementation, not native acceptance

The request owner starts before the menu-transition diorama preparation. Native fetches still use one request and one body read. A forwarding response stream observes decoded byte chunks without collecting or duplicating buffers; JSON is parsed through that stream. GLTF top-level requests use the existing progress callback once, excluding its two synthetic LoadingManager sentinels. External GLTF images and native TextureLoader fallbacks retain native counters. Far atlases reuse the world's instrumented texture loader without changing their alpha recipe or ownership. Completed HUD image/style requests are observed through ResourceTiming, without a HEAD request or another fetch. Module/worker script downloads are not asset-body streams, and their initialization remains part of preparation milestones.

The aggregate weights actual completed preparation milestones against download time: `(preparationFraction × estimatedPreparationMs + downloadFraction × estimatedDownloadMs) / (estimatedPreparationMs + estimatedDownloadMs)`. The preparation estimate is now 16,000ms (source `3a14523b`), calibrated to the rounded median exclusive-wait proxy from thirty native biome/culture runs. It replaces the initial 14,000ms pilot estimate. This is not an isolated CPU/GPU total: overlapping preparation during transfer is hidden by the proxy. See `native-30-combinations-c730ceb5.md` for the samples, outlier and concurrent-background limitations. Download time uses the union of exposed request intervals, counting concurrent transfers once, plus estimated remaining bytes/bandwidth/latency. The initial rate10Mbit/s, latency200ms and unknown-body256KiB are explicit estimates. Existing shipped manifest byte sizes improve pending estimates without network probes. Completion removes remaining-time estimates. This is estimated progress, not a timer or exact critical-path prediction.

Verified browser-cache/validated-cache or completed application-cache hits have zero download bytes and time. Fast requests and opaque zero counters do not establish a cache hit. Pending shared model/texture promises are not cache hits. ResourceTiming permits cache classification only where counters are exposed; unavailable entries remain unknown. Compressed wire Content-Length is not compared against decoded stream bytes. DOM loaders provide completion evidence but no reliable pending-byte callback. Late-discovered work changes the denominator without reversing the displayed percentage. Progress is refreshed by the existing rendering loop; UI and global maize use that same aggregate. Readiness still requires every milestone and zero pending tracked transfers.

Owners detach on cancellation, failure, menu return and completed handoff. Late native callbacks cannot update a subsequent load. The DEV-only actual application `?qa-loading=1` exposes read-only JSON in `#loading-progress-qa`; native fixture reports final transfer details. Diagnostics do not fetch or unlock anything.

Directed checks:51/51 PASS across asset fetch/transfer, cached/pending GLTF, packed resource lifecycle, far ownership, temporal download model and weighted readiness. A new DOM deduplication unit initially supplied an impossible future ResourceTiming timestamp; correcting the fixture to a completed timestamp restored the test. No application workaround was made for that artificial failure.

**Still pending:** native cold/warm/partial/throttled loading, actual ResourceTiming coverage and unknown counts, total-time/frametime overhead, failure/cancel/repeat coverage with the new owner, final matched baseline and memory acceptance. These checks do not establish production readiness or authorize a PR.
