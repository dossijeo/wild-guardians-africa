# Experimental Wild Engine spatial services

Branch `codex/wild-engine-spatial-services` is stacked on the experimental native-intent branch at `d903d827`; neither branch is merged into `main`. This avoids maintaining a second live-entity index while the action planner is under review. The production WASM and player policies are unchanged. All measurements below use a separately built candidate WASM.

## Implemented experimental read services

The shared native target index now accepts structure HP, status and material deltas. Two ordered sets hold damaged walls and damaged work centers separately by descending damage ratio, then numeric structure ID. HP-only updates advance a separate damage revision; they do not change Wild Engine's topology or action-planning revisions, nor wake the event-driven task planner. Removing a structure clears it from the index. A rejected batch leaves the native index unchanged, and the JS bridge replays authoritative state.

`getDamagedWalls()` and `getDamagedCenters()` return IDs, HP, damage ratio, status, material, revision and the exact `repairCost()` rational calculated by the game's economic authority. The `paidCoins` field is the integer debit that `transact()` would settle. A ruined module is reported separately through its status and quoted at full reconstruction cost. These queries are for **advice**: ordinary game commands still decide permission, affordability and whether a repair is actually completed.

The bridge is still experimental. A full-state replay occurs once after load; the opt-in campaign runner now observes every confirmed game event and projects relevant deltas into the native index. The game event log is capped at 200 entries, so a lightweight observer queue avoids silently dropping earlier events during a busy tick. Ordinary gameplay does not enable this advisor.

`getUnprotectedCropGroups()` now maintains a cached native grouping of living crops using the game's 1.7 m, same-species adjacency rule. Group IDs derive from the lowest numeric crop ID and remain stable until membership changes. The C++ index receives crop species and original harvest value as confirmed deltas, so the aggregate is independent of current money. A query selects each of the five animal movement profiles in Wild Engine, reads its weak-region closure certificate, and returns `protected`, `unprotected` or `unknown` with a revision and the crop IDs. No `unknown` is certified protected. Crop changes invalidate grouping; structure HP-only changes do not. Topological changes invalidate the per-profile closure certificate through Wild Engine's native revisions. This is an advisory read model; it does not decide how much to spend or automatically build walls.

`findPlantingSite(centerId)` now has an experimental nearest-first native search over resident chunks. It uses a persistent bounded-work priority queue, a live-crop occupancy grid, native terrain/prop/barrier placement checks, and native worker routes in both directions from the actual center service point. Site priority is measured from that service point, rather than the building centroid; this follows the workers' real access side. A found site can receive a provisional lease so consecutive requests do not return the same position. Releasing an unused lease reopens the search; confirming a paid `Game.plant()` call is separate from the lease and still requires the ordinary game command. Confirmed `CropPicked` and `CropDestroyed` events both release native occupancy. Results distinguish `found`, `pending`, `blocked`, `no-space` within the resident window, and `unknown` when spatial data is absent. A missing resident chunk cannot be called exhausted. The site finder is connected only to the **opt-in experimental** campaign advisor; more seeds and biomes are required before adoption.

The physical regression builds a paid ring and automatic worker door, plants inside it, confirms all five profiles classify the crop as protected, then removes actual wall modules until the graph observes a breach. The native group result then ceases to be protected. A second regression compares every group member with the existing game grouping on a frozen day-15 state, including save/load and crop-removal invalidation.

Planting regressions compare hundreds of resident Desert candidates and samples from all six biomes against `nav.placement()` and reject every false positive. A chunk-edge regression verifies that a site remains `unknown` until neighboring prop data is resident. A frozen day-15 state obtains two distinct reserved sites, verifies actual outward/return worker routes, then makes a real paid plant command and confirms the next native result does not overlap it. These directed checks do not establish full equivalence across all cultures or geometry changes.

An experimental **game-service prototype** now offers `planCropEnclosure(groupId)`. It obtains the native crop group, quotes a bounded set of rectangular strokes through the existing wall-chain rules, and previews the proposed barriers in Wild Engine before accepting a closure. The native five-profile crop certificate must report `protected`; a merely placeable stroke, a partial ring, or an `unknown` sector is never called closed. The quote exposes modules omitted by physical placement or crop overlap and the exact incremental module cost. Existing pieces on the same trace are excluded by `wallStroke()`, including pieces of other materials. A directed test verifies a speculative plan leaves the live graph unchanged, and a subsequent wall piece lowers the quoted incremental cost. This is deliberately **not yet a fully native endpoint**: gate placement, stroke geometry and worker-route witnesses still run in the game service. The bot has not adopted the new enclosure planner; it is a correctness prototype, not a measured speedup.

The existing expanding defense bot now passes its paid `previewWallChain()` quote to `buildWallChain()` for a same-state commit, eliminating the duplicate geometry quote. The game accepts a prepared quote only for the same game/nav objects, stroke options, command sequence, ID generation, simulation time, entity counts and topological revision. It uses an internal clone rather than trusting caller-mutable quote fields, then repeats permission and affordability checks before debiting the normal ledger. Changed state rejects the quote. This is a behavior-preserving optimization of the **existing** bot policy; it is separate from adopting the enclosure planner.

## Reproduction and early evidence

Build the candidate with `SPATIAL_WASM_OUTPUT=.cache/spatial-services-prototype.wasm bash tools/build-spatial-savanna-wasm.sh` in the configured Emscripten environment. Set `WILD_ENGINE_SPATIAL_SERVICES_WASM=.cache/spatial-services-prototype.wasm` and run `node --test tests/spatial-native-damaged-services.test.js`. The test checks ordering, exact repair quote, HP-only invalidation, reconstruction, removal, rejected deltas and replay after save/load. The inherited native-intent tests also pass on this binary.

`tools/experiments/benchmark-spatial-damage-service.mjs` compares hot JS filtering/sorting with the candidate endpoint using frozen states and ABBA order. In two 5,000-query runs on the Desert day-7 repair state (58 structures, four damaged walls), JS arms ranged 10.9–17.0 ms and WASM arms 12.5–22.0 ms; initial native read-model synchronization took 13.7–16.9 ms and a damage delta 0.26–0.31 ms. These tiny query timings are JIT-sensitive and show **no established throughput advantage**. The current candidate WASM with crop grouping and planting prototype is 349,249 bytes; the earlier damage-only binary was 309,698 bytes. A second Desert day-15 state has 118 structures and zero damaged walls; it likewise showed mixed order-sensitive timings. Neither microbenchmark measures the player's actual decision loop or an entire campaign.

An opt-in decision profiler separates plot placement, outward and return routes, wall strokes, previews, placements, builds and other bot work. The first run, `node tools/experiments/profile-spatial-player-decisions.mjs 14 .cache/spatial-player-decisions-baseline-14.json`, used the **legacy JavaScript Navigation** from the runner's default opening. On Sabana/712, good strategy, 14 nights, it measured **5.29 s** total `act()` time. It is **not** a Wild Engine baseline. Selected nights (milliseconds):

| --- | ---: | ---: | ---: | ---: |
| 3 | 413.5 | 193.0 | 100.5 | 17,088.2 |

| 12 | 362.2 | 84.6 | 20.9 | 26,858.4 |

This does **not** reproduce the reported 196 s player-decision / 151 s tick campaign: the source revision, navigator and workload differ. Route and wall timings are nested within plot/defense time and must not be added a second time.

The profiler now supports `wild-engine` as its fourth argument and an optional `recompute` fifth argument to compare duplicate versus prepared wall quotes. Both four-night arms used the same Sabana/712 opening, strategy and Wild Engine world. They produced identical daily living-crop, planted-crop and money triplets. Aggregate wall-clock milliseconds:

| --- | ---: | ---: | ---: | ---: | ---: |
| Recompute quote | 54,193 | 26,223 | 20,567 | 20,048 | 13,166 |

This A/B supports the narrow claim that reusing an unchanged, internally cloned wall quote removes about 20 seconds of duplicate geometry work in this four-night workload. It does not solve the remaining quote or plot-search cost, nor establish a 14-night sustained gain. Raw reports are preserved in `docs/qa/spatial-services/reports/wild-engine-player-{recompute,prepared}-4.json` with runner/policy source hashes. Each timing arm ran once; repeat AB/BA samples are still needed.

An opt-in native-advice pilot (`wild-engine prepared advice` with the candidate WASM selected through `WILD_ENGINE_SPATIAL_SERVICES_WASM`) now projects confirmed game events into the native index and consults the native site and damaged-structure lists. It retains the legacy plot search only for unresolved/exhausted native site windows. Over four nights, 214 site queries found a plot, 14 returned bounded `pending`, and **zero** fell back to the legacy plot search. Bot decision time was 467 ms and `Game.tick` 13,970 ms. This **changes spatial choices**: its daily living crops were 51/52/49/42 versus 68/68/65/72 in the prepared-quote arm. The smaller farm also reduced wall-work cost. These totals are therefore a functional pilot, not an apples-to-apples speedup or a balance verdict. The native-advice runner is opt-in; the ordinary game and production WASM are untouched.

The requested 14-night pilot ended in a real day-8 defeat with no live crops. It issued 278 successful native site leases, had 57 bounded `pending` returns and used no legacy plot fallback. Cumulative bot decisions were 12,890 ms and `Game.tick` 22,096 ms through day 8; these cannot be compared to a 14-night victory or used to infer sustained performance. The changed plot selection and smaller crop base materially changed the military/economic workload. The failed run is preserved in `docs/qa/spatial-services/reports/wild-engine-player-advice-14.json`. Native site advice therefore remains opt-in and is **not approved as a campaign-quality replacement** for the existing spatial policy. Different routes or spatial choices are acceptable; the comparison must assess survival, solvency and productivity on the same seeds. It must also evaluate enclosure plans and defensive investment before adoption.

### Campaign-outcome diagnosis and corrected site service

The same Sabana/712 control with Wild Engine terrain and the prepared-quote bot completed all 14 nights with 110 live crops and 958 coins. The first native-advice arm lost on night 8; this is a real outcome regression despite its faster decisions. A one-day differential showed why placement diverged: the native lattice initially ranked by building centroid (x=83), whereas the existing plot finder ranked from the actual worker service point (x≈87.955). The native farm was split almost evenly around the building and planted 87 crops versus 110 in the control. Moving native priority to the service point raised first-day planting to 103, but a 14-night rerun still lost on night 8. Its day-3 live crop mean distance was 12.17 m versus 8.04 m in the control.

The main defect was a missing confirmed event: ordinary harvesting emits `CropPicked`, not `CropDestroyed`. The native target/occupancy projection therefore retained harvested plants as live obstacles, forcing the finder outward instead of reusing paid, productive plots. The bridge now removes a crop on either event. A regression tests that `CropPicked` frees the exact original site for the next native reservation. The service-point priority and event correction are both in the candidate, not the production WASM.

With both corrections, a new 14-night native-advice campaign **completed all 14 nights**. The control and candidate use the same seed, biome, strategy, economic rules, attacks and Wild Engine world; their spatial choices and resulting workload differ. The candidate has 101 live crops and 776 coins at night 14, versus 110 and 958 for the control. It survived and produced a comparable farm, but its ending cash is 19.0% lower on this one seed. The result is promising, not proof of a generally non-inferior strategy. In particular, no 30- or 100-night campaign or cross-biome sample has yet been run.

| Sabana/712, 14 nights | Control site policy | Corrected native advice |
| --- | ---: | ---: |
| Nights completed | 14 | 14 |
| Live crops at night 14 | 110 | 101 |
| Coins at night 14 | 958 | 776 |
| Total bot decision time | 130.20 s | 25.47 s |
| Total `Game.tick` time | 150.46 s | 173.73 s |
| Decision + tick time | 280.66 s | 199.20 s |

The bot decision loop is 5.1× faster; the whole measured decision-plus-tick workload is 29.0% faster. `Game.tick` itself is slower because the two spatial policies generate different farms and defenses. The first-day corrected pilot planted 109 versus 110 control crops, and by day 8 the corrected candidate still had 124 live crops and 828 coins versus 138 and 722 control. Native index synchronization over the 14-night corrected run took 155 ms for 21,924 confirmed events. Raw control, intermediate failure and corrected reports are retained under `docs/qa/spatial-services/reports/` with source and candidate WASM hashes.

A second same-seed 14-night replay recorded every daily ledger category without changing the policies. Both arms again completed 14 nights with the same terminal crop and cash counts; every daily ledger delta reconciled exactly. The candidate delivered 1,416 boxes versus 1,375, earned 16,651 versus 16,405 coins, and lost 50 versus 62 crops to destruction. Its 182-coin lower closing balance decomposes exactly into **+246 income, −124 wages, −100 seeds, −240 wall construction and +36 lower repair cost**. It paid for 86 wall pieces versus 62. Consequently the candidate's lower cash is not evidence of lower agricultural output; it is chiefly a larger defensive capital commitment. It is also **not yet evidence of superior protection**: the extra paid pieces need physical enclosure and interception checks before being valued as useful assets. The exact category reports are `wild-engine-player-finance-{control,advice}-14.json` in the same directory.

Before claiming a performance win, reproduce the 196 s workload or freeze its exact state, measure synchronization and queries during normal bot actions, then compare sustained campaigns. The **remaining native endpoint**—a C++ backed `planCropEnclosure(groupId)` with reusable plans and affected-sector invalidation—is not implemented. Production event integration of the native advice endpoints remains open. The hybrid planner must not yet replace the bot's existing wall choices or represent completed economic optimization.
