# Native cooperative exterior geometry prototype

This isolated prototype starts from frozen `819436083ed98cd2b905cac2faced5805a69320f`. It does not enable an application feature, change raid scheduling, defer a raid, consume a plan, alter clocks/RNG, or modify economy, actor radii, reservations, targets, damage or navigation. There is no campaign, GPU benchmark or production approval here.

`python tools/audit_raid_exterior_cooperative.py` verifies the current 458 source/input hashes, seven original logs, independent baseline source blobs and physical snapshot hashes. The final-source directed commands in `receipt.json` passed 52/52 tests. Earlier development observations are retained separately and are explicitly not tied to the final-source manifest.

## Shared work and ownership

The original boundary-face generator remains the source of generated JavaScript. Its asserted transformations introduce resumable iteration while preserving ordered input, intersection, node lookup, sort, face and gate decisions. `python tools/prepare_boundary_faces.py --check` checks generated bytes. Sync computation, the existing worker dispatcher and cooperative preparation consume the same native generators. Independent original, non-generator boundary sources copied byte-for-byte from frozen819 are used for parity checks; comparing two consumers of the same new generator alone would be weaker evidence.

The prototype prewarmer snapshots immutable request inputs and creates a private Navigation. Each pump continues that same iterator; it never restarts at anchor zero or patches the live navigator across a yield. All five actual species radii are prepared: 1.1, 0.9, 0.97, 0.85 and 1.55. Only a complete, finite, owned and matching result is adopted into the live cache. Partial work remains private. Geometry edits cancel/close outstanding iterators and workers; disposal and late replies cannot install a partial result. Worker failures expose an error and use the actual cooperative iterator. The suite also exercises the actual application worker module in a real Node worker thread; this proves computation/transport parity, not native browser MessageEvent ownership or browser rendering.

## Actual scheduling and invalidation

`RaidExteriorPrewarmer` is experimental and is **not instantiated by the renderer, Game.tick or RaidEntryPreparer**. Its caller owns `update` and `pump`; the tests use a tight loop, not animation frames. Existing native entry/preparer/clock behavior and cold fallback therefore remain unchanged. Enabling a second independent worker alongside the existing application preparer is not proposed as production integration; a shared transport/owner and actual frame scheduling require review first.

The geometry signature includes navigation version, seed, biome, culture, terrain version, terrain config/profile, structure geometry/status/alive state/material/gates, village geometry, suppression and active shield geometry. Field replacement also invalidates ownership. Camera pose, active presentation bounds, night group, remaining positive HP, clocks and positive shield duration do not restart unchanged geometry. Requests copy RNG only for snapshot proof; they never draw from it. A change in navigation version still invalidates even if another system did not change physical geometry.

## Descriptive CPU observations and limits

The final advanced sample restores the retained native Canyon farm: 103 paid walls, 865 living crops, unchanged input gzip SHA `1b0f1a153aaf9c7adcb91b394d232886016124316570f3e90df01bb280bb4a0b`. All five radii exactly reproduce the independent frozen819 polygons (four regions each). Main graph builds are zero and the complete cache is adopted once. State serialization is unchanged.

These are single descriptive CPU observations with instrumentation, unequal preparation workloads and no ABBA, RAF, renderer or GPU measurements. They do **not** demonstrate a total-time improvement. At hypothetical one-pump-per-60Hz-frame scheduling, 872 pumps would occupy about 14.53 seconds; that is arithmetic, not measured application readiness. Earlier sample was 857 pumps, 1,047.63 ms total, 29.24 ms max step and 30.49 ms max slice; both originals are retained.

The largest step is the unchanged native `propsAt` scatter call. Native sorts, final freezing and graph helpers also remain indivisible; native entry A* is outside this geometry-only prototype and remains unchanged. Batching the ordered intersection/node loops reduces individual work but adds overall bookkeeping. A 2ms soft target was exceeded and is honestly recorded as a diagnostic limit, **not** an automatic human acceptance threshold. A caller cannot promise a hard frame budget from this generator. No further architecture was added merely to chase 2ms.

The physical group12 fixture preserves exact original initial/final snapshot hashes, ledger and save/reload behavior: all twelve actors finish at their actual exit points, four real logical hits and 43 unused strikes. This is one paid enclosure, not a campaign, advanced-farm traversal matrix or a balance result.

Production gates remain open: application prewarm lead time and moving/editing behavior, exact existing raid deadline, browser ownership/transport, peak resources and rendered traveling/loading frame stability. The worker-unavailable cold fallback remains a real blocker in the existing application; this unwired prototype must not be described as resolving it or silently delaying an incursion.
