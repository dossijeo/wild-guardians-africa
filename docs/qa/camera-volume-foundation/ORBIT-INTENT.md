# Synchronous camera input preserves orbit intent

Terrain height correction previously restored the raw eye only in `updateTerrainCamera`, during the render loop. Three.js r180 pointer/wheel handlers also invoke `OrbitControls.update()` synchronously. If a cliff moved the rendered eye high above the orbit target, that input update could reconstruct the orbit from the corrected eye and clamp its inferred radius, introducing a zoom/tilt jump before the next render.

`installTerrainCameraIntent` wraps the instance's update method. When the current eye and target match the last protected pose, it restores the original orbit eye before the native update and protects the resulting terrain pose immediately afterward. External camera/target edits remain observable. The hook preserves update arguments, receiver and return value, accepts an initially unavailable world field and restores the original method on disposal. WorldScene installs it when creating controls and releases it before controls disposal.

The [48-test regression log](intent-regressions.txt) covers terrain cameras, raid travel and raid/terrain interaction. The new real-OrbitControls case starts on a cliff where the rendered radius exceeds 65, invokes the same synchronous dolly/update path used by wheel input and verifies the intended 5% zoom rather than inferring a new radius from the cliff correction. Two hundred subsequent updates retain the same pose. Field changes, external pan edits, return-value preservation and hook removal are also covered. The [targeted final test log](intent-targeted.txt) reruns the two added cases after the unavailable-field guard was tightened.

This is a live terrain/input correction and a prerequisite for adding model exclusion without feeding corrections back into the controls. **Model collision and soft camera exclusion are still not connected.** These tests do not establish visual close-up quality, touch usability on physical devices or frame-time impact.
